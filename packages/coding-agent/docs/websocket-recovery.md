# Codex WebSocket recovery

Codex Responses can use `transport: "auto"` to try WebSockets with connection-scoped incremental context when a cacheable session ID is present. `"sse"` uses HTTP; `"websocket"` uses a WebSocket without the cached-context delta, while `"websocket-cached"` explicitly enables it. This page concerns Codex only. Direct OpenAI Responses uses HTTP and has no live provider continuation or steering.

A cached Codex request may send a `previous_response_id` and only new input on the reused connection. Pi stores detached request/response value snapshots after a completed response, not mutable transcript objects. On a new connection or without a valid baseline it sends full current input. This optimization is not proof of a provider cache hit or reduced billed tokens.

If the server rejects a missing previous response ID, Codex retries the WebSocket request once. A pre-stream WebSocket transport failure falls back to SSE for that request; a failure after stream start is reported to the agent retry policy instead of silently replaying emitted output. One pre-stream WebSocket connection-limit failure gets a separate retry. Cancellation and non-transport provider errors do not trigger transport fallback. Session fallback state is observable through Codex WebSocket diagnostics and cleared with session resource cleanup. Do not replay a tool or infer that a failed request had no effects from a missing completion record.

Assistant messages can retain redacted `provider_transport_failure` diagnostics for failed attempts. Inspect the session file shown by `/session`; request timing, transport, event, and close fields are observational and may be absent. A close code such as 1006 says no close frame arrived, not which party caused it. Byte counts do not establish provider receipt or billing. Compare successful and failed `auto` and `sse` requests under the same workload before attributing a disconnect to a backend or changing transport policy.
